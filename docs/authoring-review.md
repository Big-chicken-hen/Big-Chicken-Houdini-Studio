# 第一部分｜独立审查结论

## 1. 我的判断：核心架构基本成立，但仍有局部正确性问题；下一阶段应转向真实创作闭环

**Studio 当前没有发生方向性偏离，适合继续作为主线开发。没有充分理由再进行一轮大规模架构重写。**

但我不会把它归类为“核心已经完全稳定，只剩增加功能”。当前更准确的状态是：

> **主要模块分工、场景身份、操作收据与执行队列的设计合理；上一阶段解决了真实问题。不过，进程异常退出后的执行权归属仍有缺口，历史同步存在成本转移，真实 Houdini 验收的可独立复核程度也不足。**

这些问题应该进行有边界的修正，**不应该扩展成新的 recovery 平台、统一状态框架或第三代架构。**

下一阶段我建议交付的不是又一份 readiness 报告，而是：

**一件可以通过自然语言创建、继续修改、查看真实图像反馈的 Houdini 资产，同时补齐支撑这条工作流的关键异常路径。**

## 3. 当前架构为什么值得继续保留

### 生产链路的职责已经比较清楚

目前实际链路是：

**Launcher → supervisor 内的 Bridge → Codex App Server → MCP stdio → Houdini Runtime → 主线程 HOM → 持久化 operation receipt → Codex / Panel。**

这里不应误算进程：**Bridge 运行在 supervisor 进程中，不是又增加一个同职责的独立服务。** supervisor 负责启动与进程归属，Bridge 负责原生 Codex 会话；场景执行不需要绕回 Panel 才能发生。

最重要的边界仍然成立：

| 边界    | 当前实现                                      | 判断   |
| ----- | ----------------------------------------- | ---- |
| 场景身份  | Runtime 在真正执行 HOM 的主线程回调中检查 `scene_epoch` | 必须保留 |
| 操作事实  | queued、running、终态和详细结果由 ledger 持久化        | 必须保留 |
| 重复提交  | 同一 ID 绑定 payload hash；查询不会重跑脚本            | 必须保留 |
| 并发执行  | 场景读取、cook、capture、写入共用有界队列                | 必须保留 |
| 执行与验收 | `mutation_outcome` 和 `checks_outcome` 分开  | 正确   |
| 健康检查  | 读取缓存，不为 health 调用 HOM                     | 正确   |
| 会话历史  | 使用 Codex 原生 Thread/Turn，不另建聊天数据库          | 正确   |
| 项目资料  | 显式 memory、可选文档 FTS 独立于实时 Houdini          | 正确   |

这些并非仅存在于架构文档中：`runtime.py`、`ledger.py`、`runtime_server.py` 和 `workspace.py` 的实际实现支持上述判断。

**我没有看到需要替换这套主要模块分工的根本错误。** 当前存在的问题，更多是这些边界在异常生命周期和真实使用中的落实程度。

## 4. 上一阶段的实施质量：总体有效，不是只改文档

### 已经真正修好的部分

上一轮指出的若干问题，现在不应继续作为“未修复问题”重复列出。

**CI 分层已经修正。** 后端环境明确不安装 Qt，测试发现也排除 Qt 测试；另一个 Windows job 实际安装 PySide6，执行 UI 测试并生成截图。当前主线四个后端矩阵任务和一个 native-ui 任务全部通过，不再是之前的“backend-only 环境导入 PySide6 失败”。

**检查与错误反馈也有实质改进。** 缺失节点不会再通过“输入为空”的检查；工具 schema 明确了更多字段与约束；脚本错误保留了有界的位置和类型信息。当前测试覆盖这些具体行为，不只是检查函数能被调用。

**Panel 开始正确区分 HTTP 错误和执行结果。** 一个 HTTP 200 的 operation receipt，即使包含执行错误，也应进入收据展示，而不是被通用网络错误处理吞掉。这项修复与记录中的真实 GUI 失败吻合。

**提交前明确拒绝与提交结果未知，现在也有所区分。** `send_failed()` 根据结构化的 `submission_state` 决定是否进入 uncertain 状态，不再对所有失败一律要求 reconciliation。

**截图设置比以前更谨慎。** 当前实现修改 stash 后的 flipbook settings，并关闭一些不适合普通截图的选项，例如模拟初始化和 motion blur。SideFX 明确说明，模拟初始化可能重置模拟，motion blur 还会增加子帧计算，所以这不是无意义的防御代码。([SideFX][1])

我的总体评价是：

> **这一轮实施确实在修产品问题，没有借机重建整个平台。**

不过，历史同步这一项是“正确性改善，但成本处理仍需收尾”，下面单独讨论。

## 5. 当前最重要的问题

### 5.1 高优先级：workspace 排他保护的生命周期，短于真正的场景执行者

这是本次重新阅读后发现的最值得优先处理的问题。

当前 `WorkspaceLock` 由 supervisor 持有。对于可以进入 `finally` 的正常退出和异常路径，代码会等待仍存活的 Houdini 结束后再释放锁，这部分处理是合理的。

但是存在另一条路径：

> supervisor 被强制终止或直接崩溃 → Houdini 子进程仍存活 → supervisor 持有的锁被释放 → 用户再次启动同一 workspace。

文件锁的所有者进程结束后，操作系统会释放其锁；这不是 Python 的 `finally` 能保证覆盖的场景。([微软学习][2])

新的 Runtime 启动时，会直接打开该 workspace 的 `operations.sqlite`，并调用 `ledger.recover()`。`recover()` 将数据库内遗留的 queued/running 操作改成 cancelled/unknown，但**Runtime 本身没有另一道排他保护，证明旧 Runtime 已经不再执行和写入这些收据**。

由此推导出的风险是：旧 Houdini 尚在执行时，新 Runtime 可能把旧操作当成崩溃遗留记录处理，两个 Runtime 也可能同时使用同一 workspace 的操作账本。

**这是代码路径支持的条件性风险，本次没有在真实 Houdini 中故障注入复现。** 它也不是说普通启动已经会出现两个执行者。

需要保证的核心条件只有一句：

**只要旧 Runtime 仍可能执行场景操作，新 Runtime 就不能取得同一 workspace 的执行权，更不能先行恢复旧账本。**

这属于核心正确性的局部缺口，但不需要重写整体架构。应让 Codex选择最小的进程生命周期/排他所有权修正，而不是引入分布式租约、心跳服务或自动杀 Houdini 的恢复框架。

---

### 5.2 历史同步修复把一部分成本转移到了反复读取整段历史

当前 Panel 已加入有界缓冲、请求身份和旧 Thread 响应过滤，明显比丢弃回填期间事件更正确。

但 `Transcript.hydrate()` 仍然会：

1. 清空并重建整个 transcript；
2. 把快照中的 item ID 标记为 suppressed；
3. 后续遇到这些 item 的 delta 时，不直接应用，而是要求再次读取原生历史。

Panel 为这种情况安排了 750 毫秒的历史刷新。

这不是说每个正常回合都在不停全量刷新。**主要触发条件是：活跃回合中发生历史回填、重连或重同步，而该 item 还在持续流式输出。**

在较长、带图片的对话里，这条保守策略可能带来重复传输、重复创建控件、滚动位置跳动和额外布局计算。具体耗时尚未实测，但调用路径已经明确。

我建议局部收尾：保留现有防重复和防遗漏保证，减少不必要的全量控件重建，保持用户滚动位置，并限制活跃 item 的重同步成本。

**不要为此新增聊天数据库，也不要把整个 Panel 改成一个通用状态管理系统。**

---

### 5.3 “收据可恢复”还不等于“图片结果可恢复”

当前图片文件可以落盘，但 capture 的 `artifact_id → 文件路径` 映射保存在 `HoudiniScene._artifacts` 内存字典里；operation receipt 则在 workspace 数据库中长期存在。

因此，一次 capture 的收据在新 Runtime 中仍可能查到，而旧 artifact 的访问不一定还能成立。**这不是收据机制失败，而是产物生命周期尚未与它对齐。**

在下一阶段增加视觉反馈之前，应明确：图片结果只保证当前 session 可读，还是允许随收据跨重启读取。后者应通过受控、持久的产物引用解决，不应扩展成“任意文件路径都可以由 MCP 读取”。

同时，当前 capture 还需要真实验证图片尺寸、实际帧与恢复失败的报告方式。旧 HIA 在这些细节上有可提取实现，不必重新猜测。

---

### 5.4 长 HOM 的 Stop 体验仍没有被证明

Runtime 在另一个线程接收取消请求，并让脚本在 `checkpoint()` 处协作停止，这与“强制终止正在运行的 HOM”是不同能力。当前设计没有错误地承诺通用 Python 事务或自动安全重试，这一点应继续保持。

但 Panel 本身也在 Houdini GUI 线程中。需要真实确认：

**长 HOM 占用主线程时，用户是否还能点击 Panel 的 Stop？**

后台测试线程能发送取消请求，不能替代这项 UI 可达性验收。仓库也明确把长 cook 取消列为未验证。

这里不应直接新增 worker 平台。先测清真实行为，再决定使用更小的语义批次、协作检查点、原生可中断操作或针对明确后台渲染需求的进程。

不要把 `hou` 随意搬到后台线程，也不要用任意 `processEvents()` 处理掩盖主线程重入风险。

---

## 6. 真实 Houdini 验收：有价值，但证明范围必须缩小到实际证据

### 已经可以独立核对的部分

当前主线的 CI 配置、实际执行日志和离屏 UI artifact 可核对。它们支持：

**后端测试与 Qt 测试通过；原生 Qt 控件可以生成这些界面；Launcher 的多状态和高 DPI 预览确实存在。**

它们**不支持**“真实 Houdini、真实模型推理或完整应用重启已经通过”。CI 的离线 smoke 也明确输出 Houdini GUI 和 Codex inference 未运行。

### 确定性 Houdini smoke 的路径是合理的

我检查了 `houdini_smoke.py`。它使用真实生产 MCP 子进程、Runtime 队列以及注册的 Panel；场景创建脚本由 harness 提供，不由 Codex 生成。之后通过实际 Panel 的 HTTP 路径读取 operation receipt。

因此，它适合证明：

**生产 MCP → Runtime → 主线程 HOM → 场景 → receipt → Bridge → Panel 这一段能协同工作。**

它不适合证明：

**模型能自己理解任务、选择工具、编写脚本，并在失败后自行修正。**

这个区别在设计上可以清楚划分。该 smoke 规模仍然合理，不属于应该删除的验证基础设施。

### 自然语言任务的记录是正面信号，但不是完整产品认证

验收文档报告：真实 Panel 中的一次任务由 Codex 完成了 size-2 Box，使用 `hia_context` 和 `hia_execute_hom` 两次模型工具调用，并由用户批准了读取和创建。记录还给出了 Thread、Turn 和 operation ID。

我认为这份记录的可信之处，在于它没有掩盖限制：

* 首次 smoke 在场景操作完成后暴露了 Panel 收据展示问题；
* 修复后查询的是原 operation，没有重放创建脚本；
* 使用了更新模块并重建 Panel 的开发方式；
* 网络经历 WebSocket 超时后 HTTPS fallback；
* 记录的几十毫秒仅是 Runtime 排队与执行，不是端到端任务耗时。

但需要保留三项限制：

**第一，原始现场报告和图片未公开。** 我不能直接复核报告中描述的运行过程，只能核对文字记录、生产代码和 harness 是否一致。

**第二，这是经过开发修复、模块重载和 Panel 重建的集成过程。** 它不是“最终 main 从冷启动开始、无需开发辅助的一次完整验收”。

**第三，任务提示明确要求一个批次、回读、不要搜索截图。** 两次调用证明短路径可行，但不能证明 Codex 面对普通、不带流程提示的请求也始终如此。

因此，我对现有证据的定性是：

> **足以支持继续推进产品，尚不足以支持广泛稳定性承诺。**

下一轮需要的是少量可复核的最终版本验收，不是更厚的验证说明文档。发布脱敏的操作收据、模型工具序列、环境版本和人工干预说明即可，不需要公开账号截图或整份原生会话数据库。

## 7. Agent 效率：当前基本友好，下一步应减少能力缺口造成的返工

现在七个工具的职责基本合理，schema 比上一版明确，内部 operation ID 和场景绑定由 adapter 管理，没有要求模型自己维护一串内部状态字段。简单任务也没有被强制经过资料检索、全场景扫描或截图。

我不建议继续为了减少数字而合并工具。

还应区分两种轮询成本：Adapter 内部等待 receipt 的 HTTP 查询是程序轮询，**不是每次都让模型再次推理**。只有长操作返回后，模型继续调用 `hia_operation`，才增加模型工具轮次。是否需要增加有界等待参数，应由长任务实际记录决定，不值得提前新增推送服务。

下一阶段更可能拖慢 Agent 的，是**实时能力读取还比较基础**：

当前 geometry inspection 主要返回数量、包围盒和部分属性名；复杂参数实例、属性类型和值、实际材质绑定等信息不足时，模型就需要反复编写临时查询脚本。通用 HOM 当然能做到，但相同的诊断代码会反复生成。

**补几个高价值的定向读取，比新增一组“建模工具”更值得。** 这正是旧 HIA 可以减少重复工作的地方。

## 8. 旧 HIA：具体哪些是资产，哪些不是

### 第一类：值得直接继承的思想

我会保留这些方法，而不是继承旧框架：

**区分参数模板名和真实实例名；区分节点存在、计算成功和视觉正确；区分 cook 发生与缓存确实更新；记录截图的实际来源、帧和恢复情况；先查材质绑定，再调整着色器；动画与模拟采用有意义的代表帧。**

这些思想在旧 executor 的参数、几何、cook、capture 和动画读取实现中都有具体体现。

### 第二类：有价值，但必须提取后适配的实现

| 旧 HIA 位置／方法                                                 | 值得提取什么                                          | 接入 Studio 时的限制                             |
| ----------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------ |
| `executor.py::_parameter_templates()`、`_node_help_result()` | 实例参数名、模板模式、multiparm 索引、默认值、类型，以及定向过滤           | 接入现有 lookup/inspect；不迁移整个 catalog/cache 系统 |
| `_geometry_record()`、`_attribute_record()`                  | 各 owner 的属性类型、tuple size、array/type info、组与原生计数 | 按需返回，真正限制读取成本，不只限制返回数量                     |
| `_capture_resolution()`、`_capture_viewport()`               | viewport 比例、实际帧和图片尺寸、相机/帧恢复、捕获错误与恢复错误分开         | 保留 Studio 新加的模拟初始化等保护；不整体复制旧截图框架           |
| `_cook_state()`、`_cook_evidence_record()`                   | 目标节点的 cook 状态、次数、耗时与帧证据                         | 只针对任务需要的路径，不成为每次写入的必经步骤                    |
| `_animation_summary()`、`_keyframe_record()`                 | 关键帧、表达式、时间依赖、时间范围等真实事实                          | 定向读取，不遍历全场景所有参数                            |
| `_solaris_summary()`、材质相关读取                                 | 从实际 LOP stage 读取 prim、layer、variant 等信息         | 材质绑定要按 USD 正确解析，不能把旧启发式直接当权威               |

这些不是未来“可能存在”的资源；本次已经重新读取了对应实现。

不过，**旧实现有价值，不等于可以照搬。** 两个具体例子：

旧几何读取里有 `list(geometry.points())[:sample_limit]` 一类写法。它限制了返回样本数，却先构造了全部点的容器。应继承采样意图，不应继承这种可能放大大场景成本的实现。

旧 Solaris 读取中的 material relationship 扫描，也不能代替“最终有效绑定”的解析。USD 绑定涉及祖先、collection、strength、purpose 和 subset；应使用对应版本的 `UsdShade.MaterialBindingAPI` 解析能力，而不是找到一个 `material:binding` target 就宣布绑定正确。([OpenUSD][3])

### 知识内容可以复用，知识基础设施不必复用

旧仓库中的 MaterialX/Karma、SOP 属性、程序化曲线、Solaris 等卡片可以作为开发线索和少量任务参考。但我实际读取的 `materialx-karma-lookdev.md` 明确标注 **`community_unverified`**，部分来源版本也较早。它提供的是工作流综合，不是一套已在当前 Houdini 版本验证的可执行网络。

正确复用方式是：

**选取相关内容 → 核对当前安装和原始 API → 提炼成小实现或少量参考 → 用 Studio 验证。**

不是把旧知识库、manifest、embedding 安装器和索引生命周期一起搬回来。

旧测试也一样。viewport 测试包含大量有价值的相机、帧和错误恢复场景，但使用的是 FakeHou/FakeViewport。应继承测试场景，不能把它们描述成旧能力已获得真实 Houdini 认证。

### 第三类：明确不应迁回的历史负担

我的建议是拒绝迁入旧的双后端/B2 兼容通道、多层能力认证协议、重型 Context Pack、默认全量验收流程、自动恢复规划、启动期知识构建，以及 embedding/vector 的核心依赖。

**复用单位应该是能力函数、算法、测试场景和诊断经验，而不是旧 subsystem。**

也不要为了省事让 Studio 直接依赖整个旧 `HoudiniExecutor`。那会把旧状态、知识和错误体系一并带入。

## 9. Launcher、复杂度与 Git 的判断

### Launcher：已经有明确氛围，不需要再推倒；“科幻游戏 UI”特征仍偏弱

我实际查看了当前主线生成的界面，而不是依据提交说明评价。

[当前主线 Launcher 预览](sandbox:/mnt/data/studio-current-evidence/previews/launcher/02-selected-workspace.png)

我的视觉判断是：

**雨夜、暖灯、深青色和“让灵感亮一盏灯”的文案已经形成统一身份。它比普通企业控制台更像一个有情绪的创作入口。**

但右侧交互骨架仍比较传统，整体更接近“日系雨夜创作工作室”，而不是强烈的“未来感游戏启动界面”。这不意味着设计失败，也没有理由仅因“不够炫”再进行一次重做。

后续可以小幅强化工作室徽记、排版节奏、少量非对称结构和 workspace 身份；小窗口下适度压缩装饰区域，把空间还给配置。**不应继续把大量开发时间投入 Launcher，而真实创作链路仍停在 Box。**

技术上这轮视觉实现很克制：一张本地图片按尺寸和 DPR 缓存绘制，活动指示只更新小控件，隐藏或最小化时停止不必要动画，没有 Web frontend、视频背景或完整动画状态框架。这个复杂度与收益是相称的。

### 新版目前没有重新膨胀成平台

新增的 schema、错误定位、有限事件缓冲和小型 smoke 都有实际用途。主要成本问题是前述历史全量刷新，不是 subsystem 数量失控。

SQLite、队列、receipt、scene epoch 也不应该为了“极简”删除。它们仍在直接保护用户工作。

### Git：主线可继续使用，有一个应该收尾的旧草稿

PR #2 的 13 个提交基本按 Panel、Runtime、CI、Launcher、打包和验收分组。存在几次集成修补，但不是 `fix1/final final` 式不可读历史。一次 merge commit 不构成重写公共历史的理由。

当前遗留是 PR #1 及 `studio/product-readiness` 草稿线；PR #2 的开发分支也仍存在。Codex 应先比较是否有尚未被覆盖的独立改动，再关闭已被替代的 PR、清理完成的短期分支。**不要把旧草稿整体合回来，也不要未经检查删除独有工作。**

## A. 稳定边界：保持不变

保留 Runtime 作为场景身份、队列和 operation receipt 的权威来源。保留同一主线程回调中的 epoch 校验、同 ID 的 payload 冲突检查，以及查询结果绝不重放脚本的原则。

保留 Codex 原生 Thread/Turn、历史和审批；不增加第二个 Agent、持久聊天数据库或恢复提示生成器。

保留现有七工具方向。优先扩展少量定向查询能力，不为每一种 Houdini 操作新增一个工具。

保留文档 FTS、显式 memory 与实时场景解耦。不要把 embedding、资料导入或索引构建放回启动路径。

不修改旧 HIA、不改 Houdini 安装和用户全局配置、不覆盖用户 HIP 和无关变更。

---

## B. 优先级一：修正异常生命周期中的执行权归属

检查并复现以下场景：

> 专用测试 workspace 已启动 Houdini；supervisor 被强制终止，但 Houdini 仍存活；再次启动同一 workspace。

修复应保证：

**旧 Runtime 仍可执行时，新 Runtime 不能获得同一 workspace 的执行权，不能提前调用恢复逻辑修改旧操作状态。**

具体采用 Runtime 持锁、所有权移交或其他最小实现，由 Codex根据实际代码决定。不要扩展成通用租约系统，不要自动杀掉用户 Houdini。

验收要覆盖正常退出、可处理异常，以及不经过 `finally` 的 supervisor 消失。使用专用场景和进程，不对用户工作窗口做故障注入。

完成这一项后，应尽快进入产品能力，不再扩大架构修整范围。

建议提交边界：

```text
fix(runtime): preserve workspace execution ownership across supervisor failure
```

## C. 优先级二：完成一个真实的“创建—修改—看结果”闭环

### 交付物

选择一个有明确结构和控制参数的小型程序化资产，例如可调层数和宽度的书架，或同等规模的桌面道具。

要求通过正常 Panel 操作完成：

**自然语言创建 → 定向读取结果 → 用户提出两次增量修改 → 在原网络上修改 → 真实截图回传 → Codex 根据图像和场景事实解释结果。**

重点不是模型多精美，而是确认它能持续在当前场景里工作，不会每次重建一个新资产，也不会为了一个参数修改反复执行复杂流程。

首轮可用明确验收需求，但另保留一个不指定工具步骤的普通用户请求，避免所有效率结果都来自“只准两次调用”的定制提示。

### 在实现新 capability 前，必须先检查旧 HIA

优先查看：

```text
houdini_package/python_libs/hia_mcp_runtime/executor.py

_parameter_templates
_node_help_result
_geometry_record
_attribute_record
_capture_resolution
_capture_viewport
_cook_state
```

对每项准备采用的能力，明确其解决的问题、旧实现的依赖和限制。可以提取少量代码，也可以依据同一思路重写；**不能直接接入整个旧 executor 或旧工具注册体系。**

只在 PR 说明中简短记录来源提交、采用的函数/思路和舍弃的部分，不另建庞大的迁移清单系统。

### 首批值得补充的能力

**参数发现。** 支持目标节点的真实参数实例，特别是 multiparm 展开名称；不能只给模板模式，让模型猜实际名称。

**几何读取。** 在现有 inspect 中补足任务需要的属性 owner、类型、tuple size 和有界样本。使用真正有界的读取方式，不先取全部几何对象再切片。

**图片反馈。** 校验实际图片尺寸与帧，正确报告捕获和恢复失败；明确 artifact 生命周期，并让收据引用的图片可以按承诺读取。保留本地受控产物边界，不增加任意文件访问入口。

这些能力都是为完成上述资产闭环服务，不要求本轮实现完整的 Houdini inspection 平台。

建议提交边界按实际变更选择：

```text
feat(houdini): add targeted parameter and geometry inspection
feat(capture): complete the native image feedback path
```

## D. 与产品闭环一起完成的验收

### 从最终版本冷启动，不靠开发状态通过

本轮至少完成一次：

**正式启动入口 → 当前 main 对应代码 → 新 workspace → 原生登录/审批 → Panel 请求 → 真实 Codex → 真实 Houdini。**

不热重载生产模块，不手动替模型修创建脚本，不修改数据库让结果通过。发生开发辅助时如实记录，并在修复后重新进行无辅助运行。

此前的开发验收可以保留，但不能替代最终版本冷启动验收。

### 记录四种不同事实

每个用例分别记录：

| 事实   | 要回答的问题                        |
| ---- | ----------------------------- |
| 模型行为 | Codex 自己调用了哪些工具？是否生成了脚本？      |
| 运行结果 | 哪个 operation 执行了，副作用和检查结果是什么？ |
| 产品体验 | 用户等待多久，审批几次，UI 是否可操作？         |
| 验收方式 | 是否使用确定性 harness、热重载或人工修正？     |

程序内部 receipt 查询不计为模型工具轮次；Runtime 执行时间不当成端到端耗时；成功截图不等于视觉质量自动通过。

输出少量脱敏证据即可：版本与 commit、工具调用序列、收据、必要图片、耗时和辅助说明。不要公开账号信息、token 或完整会话数据库。

### 高风险边界的最低集合

在专用测试场景中逐步完成：

**同路径 HIP 重载后拒绝旧观察；queued 操作取消；长 HOM 期间真实 Panel Stop 的可达性；操作响应丢失后查询同一 ID，副作用只发生一次；Houdini 重启后的收据与产物读取。**

其中长 HOM 测试不能由后台线程替用户点击 Stop 后宣称 UI 已验证。不能安全中断的操作，应明确显示限制并改善批次组织，而不是强行提供虚假的即时取消。

不需要一开始搭完整故障平台。围绕现有生产入口做少量专用测试即可。

建议提交：

```text
test(houdini): verify cold-start authoring and interruption boundaries
```

## F. 下一项能力：在同一资产上完成最小 MaterialX / Karma 工作

**不为这一个渲染任务提前建设通用 job scheduler。** 确实需要后台渲染时，再依据具体输出和进程生命周期增加最小能力。
