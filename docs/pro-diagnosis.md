# 总体判断

**这个项目的核心路线是成立的，但核心执行边界还不够可靠，外围能力已经比核心执行协议成熟得更“复杂”。**

我不会建议推倒整个项目，也不会建议继续沿着现有结构不断补 validation、recovery 和状态标志。

我的建议是：

> **保留 Codex App Server、批量 HOM、Houdini 主线程执行、原生图片回传这条主干；对“场景身份、操作生命周期、结果确认”做一次有边界的架构重写；把 knowledge、启动、恢复从这条执行主干中解耦。**

最需要优先解决的，并不是“向量数据库是不是多余”，而是：

**一次操作究竟针对哪个场景、是否已经执行、执行到什么程度，以及断线或 Stop 之后系统凭什么知道答案。**

下面先说明审查基线，再分别给出当前判断、目标架构和重构路线。

# 一、当前项目的真实状态

## 1. 实际运行方式：主执行通道并没有想象中那么绕

当前默认运行方式可以概括为：

| 阶段                    | 实际实现与职责                                                            |
| --------------------- | ------------------------------------------------------------------ |
| 启动                    | PowerShell launcher 准备环境、会话目录和 token，先启动 Bridge，再启动 Houdini        |
| Panel → Bridge        | PySide Panel 通过本地 HTTP 提交输入、查询状态、接收事件                              |
| Bridge → Codex        | Bridge 管理 `codex app-server`，通过 stdio JSON-RPC 调用 Thread/Turn 等接口  |
| Codex → MCP           | Codex 调用独立的 `hia_mcp_v2` stdio 服务                                  |
| MCP → Houdini runtime | MCP adapter/transport 通过带认证的 loopback HTTP 请求 Houdini 进程内的 runtime |
| runtime → HOM         | runtime 将场景操作调度到 Houdini UI 主线程                                    |
| HOM → 结果              | 执行 HOM，收集结果、差异、可选验证与执行证据                                           |
| 结果 → 用户               | 结果返回 Codex；Codex 的消息和工具事件再经 Bridge 回到 Panel                        |

这里有一个重要澄清：

**Bridge 并不是每次 HOM 调用都必须经过的中转站。** 它主要承载 Panel 和 Codex 会话集成；实际工具执行由 Codex 的 MCP 子进程直接请求 Houdini runtime。启动代码、runtime 的 UI-ready 接入与 executor 分派都支持这一点。

这个进程拆分本身是合理的。**我不认为现在应该先把 HTTP 换成另一种 IPC，或者为了少一个进程把所有东西塞进 Houdini。** 相比这些改动，下面的执行语义问题更重要。

### 图片路径也基本走对了

用户附件先复制到 `.runtime/attachments/<thread-id>`，再作为本地图片交给 Codex。截图结果则由 MCP adapter 转换成真正的 image content，而不是只向模型返回一个图片文件路径。这条路线值得保留。

## 2. 你的一些怀疑成立，但有几项需要纠正

### 不是“工具数量已经失控”

当前 HIA 默认工具集是 **18 个工具**，而且已经提供批量 HOM 和批量查询。它并不是把“创建节点、设参数、连线”全部强制拆成逐节点工具调用的设计。

真正的问题是这些工具之间存在职责重叠，以及提示词和返回结构可能诱导额外的检查轮次。**18 这个数字本身，不足以证明 Agent 性能差。**

### 不是“每次调用都在跑向量检索”

检索默认是 `lexical`，launcher 默认 embedding profile 也是空值。不能把所有运行延迟都归咎于 embedding。

但是，**embedding 相关契约和知识初始化仍进入了默认启动流程**。所以“默认不使用向量查询”并不等于“默认启动已经摆脱向量基础设施的依赖”。后面会具体解释。

### 不是“每次执行都会全场景扫描和截图”

默认执行差异是 targeted diff；测试还明确保护了“默认不走全场景 snapshot”。截图也不是每次执行后的固定步骤，开发指令要求的是视觉任务里程碑截图。

这些都是正确的优化，不应该重构时丢掉。

### 旧系统确实是负担，但未必是默认运行的主要耗时

Panel 中旧 B2 场景读取与轮询，只在 `fxhoudini` 后端启用，默认 V2 不走这条轮询链路。因此，删除它主要降低维护成本，不能直接承诺大幅提升默认执行速度。

不过旧 B2 的启动契约仍然是默认 launcher 的必经检查：即使走 V2，也要求 Bridge 返回旧的 profile、schema version 和 digest。这属于**运行依赖残留**，而不只是放在目录里的历史文件。

## 3. 最值得保留的设计

**第一，Codex 负责理解和编排，HOM 负责实际执行。**

`hia_execute_hom` 提供通用批量编排，没有把 Houdini 限制在固定节点白名单里；安装版本中的节点和参数可以动态发现。这直接服务于你的产品目标。

**第二，场景操作正确地进入 Houdini UI 主线程。**

executor 默认使用 `hdefereval.executeInMainThreadWithResult`，而 knowledge 和 memory 走单独分派，不是把所有检索计算都硬塞进 GUI 主线程。Context Pack 的非实时补充也是在主线程快照之后处理。

**第三，没有把所有“效果未证明”都当成必须自动 Undo 的错误。**

测试明确区分执行完成、变化未证明和回滚。一个模型没有达到视觉要求，不意味着应该自动撤销用户可能认可的部分工作。这种区分要保留，只是返回契约需要更清晰。

**第四，已经有一些真正有用的安全与诊断基础。**

独立 token、loopback 监听、限定路径、拒绝盲目重复写入、执行阶段计时、图片内容回传，都不是装饰性基础设施。重构应复用这些能力，而不是为了“干净”重新写一遍。

## 4. 最大的架构问题：身份和状态边界没有分清

### 4.1 插件安装目录，被同时当成了用户项目

现在多个概念共用 `project_root`：

* 插件源码与安装根目录；
* Codex 工作目录；
* knowledge 数据库根目录；
* project memory 根目录；
* 启动、缓存、附件和部分会话状态根目录。

launcher 从自己的脚本位置解析根目录，再把它传给 Bridge 和 Houdini。memory 虽然有 `scope`，但默认值只是 `"project"`，不是自动绑定当前 Houdini 项目的稳定身份。

**这是比“数据库用什么”更根本的问题。**

同一套插件打开两个不同的 Houdini 项目，并不会自然得到两个清晰隔离的项目记忆空间。与此同时，普通场景操作的 Codex 又以插件仓库为工作目录，仓库开发规则与场景创作规则容易混在一起。

这还不是说“所有记忆都会错误串用”，因为你提供了手动 scope；问题是：**正确隔离依赖约定，而不是产品身份模型。**

下一版必须明确区分：

`app_root`、`workspace_id/root`、`launcher_session_id`、`scene_epoch`、`operation_id`。

不解决这个问题，只把 `knowledge_index.py` 拆成几个文件，没有改变架构。

---

### 4.2 写入绑定的是 Houdini 进程，不是被观察过的那个场景

这是一个高优先级风险。

`_runtime_binding()` 实际比较的字段是：

```text
identity_version
launcher_session_id
houdini_pid
executor_module_path
```

**没有场景代次，也没有要求写入基于哪个 HIP 状态。** HIP 路径虽然出现在状态信息中，却不属于写入绑定条件。

因此存在这样的路径：

> Codex 读取场景 A → 用户在同一个 Houdini 进程里打开场景 B → Codex 提交针对 A 的脚本 → 进程身份检查仍通过。

另外，当前身份比较发生在 HTTP handler 中，之后才调度实际执行；它不是在真正进入 HOM 的同一个主线程执行段里完成场景前置条件检查。

**建议：必须在主线程执行入口校验 `scene_epoch`。**

这个 epoch 应在打开、清空或替换场景时改变；不能只用 HIP 路径，因为同一路径重新加载也可能已经是另一代场景。

对于普通参数编辑，可以进一步对目标节点或关键值做窄范围前置检查，不必因为场景任意角落变化就拒绝全部操作。

---

## 5. 最危险的执行问题：系统没有一份足够权威的“操作收据”

### 5.1 请求失败，不等于 HOM 没执行

runtime 当前基本是同步的 HTTP 请求—响应模型。

代码明确处理了这样的情况：客户端已经超时或断开，但进入 HOM 的调用仍然继续；最终结果发送时发现连接断开，就直接返回。另一方面，结果超过大小上限，会在执行完成之后被替换成 `RESPONSE_TOO_LARGE` 错误。

也就是说：

**场景已经改变，但原调用者拿不到对应的完整执行结果，是当前协议允许发生的情况。**

现有 request ID 用于关联请求，但从这条处理路径看，它没有承担“可按 ID 再次查询已完成操作结果”的职责。

这才是许多 recovery 和状态标志不断增加的根源：

> 缺少执行端事实，只能从最后一个工具事件、连接状态、dirty 和后续 context 去推断。

这些推断有价值，但不应该成为最终执行状态的权威来源。

### 5.2 确认了一处错误的安全重试判断

在 `executor.py` 的异常回滚路径中，代码验证 Undo 栈恢复、dirty 状态恢复之后，会把：

```python
failure["automatic_retry_safe"]
```

改成可能为 `True`。

判断中使用：

```python
failure.get("external_side_effects_possible", False)
```

但这一异常创建路径没有把外部副作用明确标记为可能存在，而执行的是通用 Python/HOM 脚本。

一个直接反例是：

> 脚本修改了节点，同时写出一个文件，随后抛出异常。Houdini Undo 成功了，但文件副作用没有撤销。

因此：

**“Houdini Undo 已恢复”不能推出“整个批次可以安全重试”。**

SideFX 对 `hou.undos.group()` 的定义是把 Houdini 的撤销操作归组，不是给任意 Python、文件系统和外部进程提供事务。([SideFX][1])

这里也要避免夸大：开发指令另外禁止原样盲重试，所以这不等于当前系统一定会自动重复执行。但**接口正在提供不应被信任的安全信号**，应立即修正。

对于通用 HOM：

* 默认外部副作用是 `unknown`；
* 自动重试默认不安全；
* Undo 成功只陈述其能够证明的局部事实；
* 只有明确定义了幂等性或副作用边界的操作，才允许更强保证。

### 5.3 Stop 的语义必须拆开

当前 Stop 会先请求 Codex 中断，短暂等待后可能重启 App Server，但已经进入 Houdini 的 HOM 不会随之被终止。相关常量中，中断宽限是 1 秒，之后存在单独的恢复流程。

App Server 自身也把“中断请求已返回”和“Turn 最终进入 interrupted 状态”区分开，后者需要终态事件确认。([GitHub][2])

下一版 UI 必须能分别表达：

**Codex 已停止继续推理；Houdini 操作仍在执行；当前场景写入结果尚未确认。**

这不是多加几个按钮文字的问题，而是要求 runtime 拥有独立的操作生命周期。

## 6. 程序性能：已定位到的实际成本

### 6.1 知识构建不应该阻塞 Houdini 启动

这是目前最明确的启动关键路径问题。

`Invoke-HiaKnowledgeBootstrapOnLaunch` 在启动 Bridge/Houdini 之前同步运行：

* `bootstrap`：超时上限 180 秒；
* 当返回 `installation.installed` 且存在 pending chunks 时，再运行 `build`：超时上限 3600 秒。

**这些是代码配置的超时上限，不是我测得的正常启动时间。** 暖缓存可能很快，条件不满足也不会构建。但机制本身已经证明：

> 用户只是想打开 Houdini，却可能先被可选检索基础设施拦住。

即使最终异常被捕获并继续启动，前面的等待已经发生了。

此外，lexical 模式仍要加载 embedding launcher contract，验证恰好两个 profile，并检查相关运行布局。这使“不使用 embedding”的基础启动仍依赖 embedding 子系统的正确性。

**建议直接移出启动关键路径。** 安装、导入、索引构建应是显式维护任务；启动时只打开现成索引，索引不可用则降级。

### 6.2 健康检查混淆了“进程活着”和“UI 当前能执行请求”

Panel 的 V2 状态轮询调用 Bridge；Bridge 的 runtime health 超时为 0.75 秒，而 runtime 构造身份信息时读取 HIP 状态又会进入 Houdini 主线程。

据此可以推断：较长的 HOM/cook 占用主线程时，健康检查可能失败，即使 runtime 进程和原操作都仍正常存在。

我没有实测这种状态闪烁的频率，但**协议上已经无法干净地区分 busy 与 unavailable**。

应拆成：

* 不需要执行 HOM 的进程/服务存活状态；
* 主线程忙碌状态；
* 带时间戳的最近场景快照；
* 当前操作的独立状态。

### 6.3 返回结果存在确定的重复序列化

`adapter._tool_result()` 把同一结果同时写进 JSON 文本和 `structuredContent`。

可以确定的是，传输和序列化层有两份内容；**不能仅凭这一点断言模型实际收到了两倍 token**，那需要检查具体 Codex 消费方式。

但结合大量执行证据、diff、validation、warning 和嵌套状态，结果体膨胀值得优先收敛。详细诊断应该可按需读取，不应该每次都塞进模型工作上下文。

## 7. Agent 性能：问题更像“流程税”，不是 Python 不够快

当前开发指令已经照顾了简单操作：已知参数和连线不强制检索，Context Pack 也建议关闭，这是好的。

但复杂任务指令又规定：按阶段执行后 fresh cook，再使用 `hia_scene_diff/hia_validate`。与此同时，`hia_execute_hom` 自己已经支持差异和后置检查。**两者存在形成重复验证调用的可能。**

问题不在“复杂任务不该分阶段”。分阶段是必要的，尤其是视觉资产、材质和模拟。

问题在于：

> **每个阶段需要证明什么，应由该阶段的目标决定，而不是固定经过同一串工具。**

例如，改变一个已知粗糙度参数，需要参数回读；不需要同时证明拓扑、几何接触、全局网络布局和视觉构图。

我对目前 Agent 层的主要判断是：

**它已经有正确的批处理能力，但越来越多的质量要求被编码成全局长提示和多层证据对象，尚未形成足够轻的任务专属执行契约。**

像装配接触、负约束、材质入口、模拟代表帧等要求，应保留其能力，但按任务启用，而不是让每一轮场景工作都承担所有领域规则的认知成本。

## 8. Knowledge / retrieval：应该保留什么，删除什么

我的判断不是“全部删掉”，而是：

> **保留本地帮助、结构化查询、FTS 和明确的项目决策；把 semantic retrieval 从核心产品基础设施降为可独立启用的增强能力。**

### 8.1 从真实查询类型分配信息来源

| Agent 实际需要回答的问题              | 最合理的信息来源                                         | 是否需要向量检索       |
| ---------------------------- | ------------------------------------------------ | -------------- |
| 当前安装里这个节点类型是否存在？参数内部名是什么？    | Houdini runtime 的 node type / parameter metadata | 不需要            |
| 当前节点连到了哪里？材质绑定是什么？某帧几何是否为空？  | 当前场景的定向读取                                        | 不应该用知识库替代      |
| 某个 HOM 方法、参数含义、报错字符串怎么解释？    | 对应版本帮助的 exact lookup + FTS                       | 通常不需要          |
| 当前版本某个复杂 Solaris、材质、模拟流程怎么搭？ | 有来源和版本信息的文档、少量工作流资料                              | FTS 优先，必要时补充语义 |
| “以前那份教程里，用另一种说法讲过这个效果”       | 用户自己的教程、笔记、转录资料                                  | 这是语义检索较有价值的场景  |
| 当前项目约定的单位、命名、输出目录、禁止修改区域是什么？ | workspace 范围内的结构化决策/记忆                           | 通常不需要          |
| 通用矩阵、VEX、程序编排怎么写？            | Codex 推理，结合必要的运行时/API核对                          | 不应强制检索         |

这里的关键是：**runtime state、API metadata、文档知识和项目约定，不应该只是同一个检索系统里的不同 source 标签。它们有不同的真实性、失效条件和使用方式。**

### 8.2 现有向量实现不是独立向量数据库，但有规模成本

当前是 SQLite 中存储向量，再由 Python 扫描匹配向量，逐查询计算：

```python
math.fsum(map(operator.mul, query_vector, vector))
```

在完整向量层下，会扫描符合来源条件的向量；未完整构建时，又可能只在 lexical candidates 中做向量排序。

这意味着：

**完整扫描的主要计算量随查询数 × chunk 数 × 向量维度增长。** 流式读取控制了部分内存成本，却没有消除扫描计算成本。

但这仍然不证明你的当前知识量已经慢，也不证明应该立即引入另一个 ANN 数据库。

我会先问：**这些额外召回结果是否真的减少 Houdini 任务失败和工具轮次？**

在我审查到的实现和 CI 证据中，没有看到足以回答这个问题的真实任务对照结果。现有检索正确性测试，不能直接证明 Agent 工作效率收益。

### 8.3 当前 memory 的部署位置不合理

Bridge 的 project-memory 接口明确要求 live HIA V2 runtime，然后通过 runtime 工具操作数据库。也就是说，一项本来不需要当前场景的持久化决策管理，依赖 Houdini runtime 可用。

而记录记忆在数据库提交后还调用 `_vectorize_documents()`。即使实现可以降级，这仍然把“保存一条决策”和“维护检索增强层”连在了一次操作中。

**建议把 memory 放到 Bridge/workspace 数据层。**

写入成功应由持久化提交决定，不由 embedding 是否成功决定。记忆索引可以之后显式构建或增量更新。

### 8.4 我会怎样裁剪

保留 SQLite。它不是问题。

保留文档来源、Houdini 版本、内容哈希和明确的记忆更新/替代关系。

从默认运行链移除 encoder 安装检查、向量构建和复杂资料导入。Office、媒体侧车文本、批量资产导入等能力可以存在，但应该成为可选工具，而不是 Houdini 场景控制核心必须承担的产品面。

另外，开发用的架构、roadmap、诊断文档不应和日常 Houdini 创作知识默认混检；当前本地知识索引确实收录了这类项目文档。应将“开发插件”和“使用插件创作场景”的资料空间分开。

**语义检索重新进入默认配置的条件，应是实际任务收益，而不是它已经写完。**

## 9. Tests、CI 与安全边界

### CI 当前不是可靠的发布关卡

我读取了 `main` 最新 Actions job 的原始日志，其结果是：

```text
Ran 1269 tests in 208.458s
FAILED (failures=2, errors=6, skipped=2)
```

六个错误集中在 knowledge asset 测试清理目录时，SQLite 文件仍被占用；两个失败分别涉及 embedding 安装路径长度和发布预检要求本地 `.venv`。对应运行与 job 均明确处于失败状态。

Beta 候选提交没有查到对应 Actions 运行。当前 workflow 的 push 分支是 `main/master`，没有覆盖 `release/*`。这不等于候选版从未被人工测试，但意味着**仓库没有给出这次候选提交通过 CI 的证据**。

另一方面，测试并非没有价值：targeted diff、未证明变化、Undo 边界等已有具体测试。问题在于相关测试使用 `FakeHou` 和直接执行 callback 的 runner，无法证明真实 GUI 调度、cook、截图、取消和场景切换的行为。

还有一个可直接修复的代码错误：`session.py` 的 `_permission_write_targets()` 在处理 special root 权限时引用 `system_drive`，但该函数没有接收这个变量；上游计算的是另一个函数中的 `resolved_system_drive`。这类未定义名称问题应由静态检查提前抓住。

### 安全上应承认：这是受信任的本机自动化，不是 Python 沙箱

`exec(compiled_script, namespace, namespace)` 在 Houdini 进程里执行通用 Python。路径验证和 Codex 的工作区约束，并不会自动把这个 Houdini 执行环境也变成文件系统沙箱。

这不意味着应该取消通用 HOM；通用 HOM 正是产品价值所在。

但产品必须诚实定义边界：

**允许受信任 Agent 操作本机 Houdini，与保证任意脚本不会产生进程外副作用，是两种完全不同的承诺。**

我不建议再造一套复杂 AST 规则，假装能完整隔离任意 Python。优先保护会话绑定、操作归属、输出路径和用户确认边界，并让插件安装目录不再是普通场景 Agent 的可写工作区。

# 二、这个产品下一版应该是什么样

## 1. 目标不是更少文件，而是更少权威来源

我建议下一版按下面的责任划分：

| 部分              | 应拥有的职责                                       | 不应继续拥有的职责                   |
| --------------- | -------------------------------------------- | --------------------------- |
| Panel           | 输入、会话展示、选择与图片交互、操作状态显示                       | 推断 HOM 是否完成、驱动复杂恢复流程        |
| Bridge          | Codex 集成、workspace/session 管理、事件投影、本地文档与记忆服务 | 从“最后一个工具”猜测场景执行结果           |
| Codex           | 理解、规划、生成 HOM、解释结果                            | 手动维护大量内部运行 ID 和协议状态         |
| MCP adapter     | 小而明确的工具协议、参数校验、结果投影                          | 重复的业务状态机和强制工作流              |
| Houdini runtime | 场景操作唯一执行权威、主线程队列、操作结果与场景身份                   | 承载项目文档导入和向量平台               |
| Launcher        | 安装/选择运行环境、启动与进程清理                            | 在日常启动时构建知识库、解释 Goal 并生成恢复任务 |

保留独立 Bridge、Codex App Server 和薄 MCP adapter 是可以接受的。**进程隔离解决了真实问题；现在不值得仅凭进程数量把它们合并。**

Codex 的 Thread/Turn 历史继续使用 App Server 的原生机制，不再发展第二套聊天历史或摘要系统。App Server 本来就提供持久 Thread 和可恢复会话这一抽象。([OpenAI][3])

---

## 2. 核心重写：一个真正的 Scene Operation Runtime

这是我建议重写的中心，而不是整个 `executor.py` 全部重写。

每个操作应至少有：

| 字段                 | 目的                                |
| ------------------ | --------------------------------- |
| `operation_id`     | 可重复查询的操作身份                        |
| `payload_hash`     | 防止同一 ID 被用于不同脚本                   |
| `scene_epoch`      | 绑定被观察过的场景代次                       |
| `state`            | queued / running / finished 等执行状态 |
| `mutation_outcome` | completed / partial / unknown     |
| `checks_outcome`   | passed / failed / not_run         |
| `result_ref`       | 详细结果或诊断记录                         |
| `timings`          | 排队、HOM、验证、截图等实际耗时                 |

这些内部身份应主要由 Bridge/adapter 管理，**不要让 Codex 每次自己拼十几个状态字段**。

但自动管理有一个前提：它必须携带“这次工作读取时绑定的场景”，不能在写入前偷偷刷新成最新场景，从而掩盖 stale 操作。

### 执行结果先成为事实，再尝试回传

操作在 runtime 结束后，先保存结果收据，再响应 HTTP。

客户端断开后，通过 `operation_id` 可以重新取得同一结果；不能把“重新拿结果”实现成“重新执行脚本”。

这只需要一个小型、明确的操作记录机制，不需要引入完整事件溯源平台。

同时必须承认：

**进程在场景改变之后、结果持久化之前崩溃，仍可能产生 unknown。** 不能宣称任意 HOM 获得了跨进程 exactly-once 保证。新设计的价值，是把不确定性限定并显式呈现，而不是用更多布尔值掩盖它。

### 所有接触场景的操作，进入同一个受控队列

不是只有写入需要管理。

会触发 cook 的检查、切帧、截图和临时修改参数的实验，也应受同一场景执行调度管理。文档搜索和记忆读写则完全绕开该队列。

主线程队列要有明确的接纳上限、busy 状态和操作归属，不能只依赖 stdio 端“一个 write worker”作为整个系统的串行保证。

### Cancel 按实际能力定义

排队中的操作可以取消并保证不开始。

已经进入 HOM 的操作只能在安全的协作边界停止；无法安全中断时，就显示“停止后续操作，等待当前操作结束”。

不能把杀掉 App Server 等同于取消 Houdini 修改，也不能为实现 Stop 悄悄重载整个 HIP。

---

## 3. MCP 应按 Agent 的决策划分，而不是按内部模块划分

我会以大约下面这组核心工具为起点。**不是认为七个一定比十八个好，而是每个工具应该回答一个明确的问题。**

| 工具方向        | Agent 需要做的决定              |
| ----------- | ------------------------- |
| `context`   | 我当前操作哪个场景、选择和网络？          |
| `inspect`   | 我需要哪些具体实时事实？支持一次请求多个定向视图  |
| `lookup`    | 我缺的是哪个 API、节点、参数或工作流信息？   |
| `execute`   | 执行一个语义批次，并返回约定的观察与检查      |
| `capture`   | 在哪个里程碑、哪个帧和视角查看视觉结果？      |
| `operation` | 长操作/断线后的结果是什么，能否取消？       |
| `memory`    | 显式记录或读取当前 workspace 的稳定决策 |

具体调整：

**`hia_search_capabilities` 不应继续成为另一次常规工具发现轮次。** 如果所有工具已经由 `tools/list` 提供，它的价值有限；要么删掉，要么实现真正按需加载，而不是两次列出相同能力。当前 adapter 确实另外维护和搜索 capability catalog。

`scene_graph`、各类 summary 和 `scene_diff` 可以成为 `inspect` 的定向视图；但不要合并成一个有几十个互斥参数的怪物，要使用清晰的小型查询结构。

`validate` 的核心能力应成为可复用检查库：既能被 `execute` 调用，也能独立检查现有场景，而不是让每个成功执行都再支付一次额外工具调用。

`run_effect_experiment` 可以保留为可选专用能力或配方。它不是无价值，但不必成为每个普通建模任务都需要理解的核心工具。

### 返回结果默认应该很小

一次普通参数修改，返回这些就足够：

> 操作完成；修改哪个参数；回读结果；检查通过；operation ID。

完整网络证据、详细 diff、异常栈、历史观察、截图元信息，放到可按需读取的详细结果里。

**不要为了模型可能需要某个信息，就默认把所有信息都返回。**

---

## 4. Validation 应保留，但要变成“按声明提供证据”

我不会删除 validation，也不会让 `execute` 只返回“脚本没报错”。

应该区分三种证据：

**结构证据**：节点、连接、参数、材质绑定是否符合要求。

**计算证据**：目标输出是否 cook 成功，几何/属性/场是否满足可计算条件。

**视觉证据**：画面是否达到外观目标。

三者不能互相冒充：节点存在不能证明模型像参考图；截图看起来正常也不能证明动画全部帧或几何接触关系正确。

但不是每个任务都需要三种证据。

例如：

| 任务         | 合理执行闭环                      |
| ---------- | --------------------------- |
| 改一个已知参数    | 必要的目标读取 → 一次执行并回读           |
| 创建一个已知的小网络 | 一次批量创建 → 检查输出与关键连接          |
| 修改材质外观     | 读取绑定和相关节点 → 批量修改 → 需要时渲染/截图 |
| 复杂参考建模     | 形体、结构、细节等语义阶段；在决定下一步的里程碑观察  |
| 动画/模拟      | 检查相关状态与代表帧，不把单帧截图当成全部成功     |

这样既避免“一口气写巨型脚本”，也避免“每个阶段固定跑一串检查工具”。

---

## 5. Knowledge 的目标形态：轻量服务，而不是另一个产品中心

下一版默认配置，我会设计成：

**实时 metadata + 小型本地帮助索引 + workspace 决策。**

Exact lookup 先解决精确符号；FTS 解决文档和错误字符串；只有确实需要跨措辞、跨语言或异构私人资料召回时，才启用语义增强。

检索策略主要由程序处理，不必让 Codex 在每次调用前纠结 `lexical/vector/hybrid`。

语义增强的评估不能止于检索命中率，还应比较：

**最终任务成功率、首次执行成功率、工具轮次、总耗时、模型输入量和错误版本资料使用率。**

一个向量方案即使命中更多资料，如果让 Codex 阅读更多无关内容、增加一轮查询，却没有降低任务失败，它就没有证明自己的产品价值。

# 三、从现在走到目标：有边界的重构路线

## 第一阶段：先恢复可信基线，修复高风险语义

**收益最高，改动范围相对可控。**

先让默认分支和 release 候选都实际跑 CI，修复已看到的 SQLite 生命周期、路径长度和发布预检问题；加入未定义变量检查。不要用忽略清理异常的方式掩盖资源未关闭。

同时立即修复两个执行问题：

**通用 HOM 不再根据 Undo 成功宣称可安全重试；写入必须绑定场景代次。**

这一阶段就加入针对性的故障测试：

* 读取后切换 HIP；
* 提交后连接断开；
* 返回结果过大；
* 操作已执行但响应丢失；
* Stop 时 HOM 仍运行；
* HOM 异常伴随外部副作用。

**完成标准：这些情况不再被误报为“未执行”或“安全重试”。**

---

## 第二阶段：重写操作生命周期，不重写全部 Houdini 能力

重写边界限定在：

**runtime 请求接纳、主线程调度、场景身份、操作状态、结果保存与查询。**

现有节点检查、参数读取、几何 summary、图片捕获等业务函数可以复用。不要同时重写 Panel 渲染、文档导入和所有 HOM 辅助逻辑。

Bridge 和 Panel 改为读取权威 operation 状态，逐步删除通过最后工具事件推断执行状态的逻辑。

**完成标准：一次写入丢失 HTTP 响应之后，可以查询原操作结果；查询不会再次执行脚本；新场景不会接受旧场景操作。**

这是一次真正的架构重构，因为改变了状态的权威来源，而不是文件布局。

---

## 第三阶段：降低 Agent 的流程成本

收敛 MCP 工具职责、压缩默认返回、把检查并入语义批次，并重写全局开发指令。

保留几条全局原则：正确场景、明确副作用、单一场景执行权威、不盲重试、不冒充视觉验证。

将具体领域要求移动到任务 brief、按需能力说明和检查参数中。

与此同时建立固定任务集：简单参数、连线、已有网络局部修改、新资产、材质、动画/模拟、参考图任务和故障恢复。

分别记录：

| 程序指标                    | Agent 指标         |
| ----------------------- | ---------------- |
| 启动到可用                   | 完成任务的总工具调用数      |
| 排队时间                    | 检索与重复 inspect 次数 |
| HOM / cook / capture 时间 | 默认 schema 与返回体大小 |
| 结果序列化与 IO               | 首次成功率、返工轮次       |
| UI 忙碌与超时                | 端到端任务耗时及最终质量     |

**完成标准：简单确定任务明显减少不必要轮次，复杂任务不因减调用而降低成功率。** 具体提速幅度由测量决定，而不是预先承诺。

---

## 第四阶段：把 knowledge / memory 移出核心执行链

默认启动不再构建索引、不再验证不使用的 encoder profile。

Memory 改为 workspace 服务，不依赖 Houdini runtime 存活；保存和向量化分离。

保留 exact/FTS、来源和版本信息；将复杂导入、encoder 安装、向量构建作为可选组件。已有私人资料和记忆需要导出/迁移，**删除子系统代码不等于删除用户数据**。

**完成标准：没有 embedding 环境、知识索引损坏、Houdini 暂未连接时，基础启动和非场景的项目记忆管理仍正常工作。**

---

## 第五阶段：收敛 launcher 和 recovery

Launcher 只负责启动、进程归属和运行环境，不再充当懂 Goal、懂失败步骤、会组织恢复提示的任务控制器。

当前自动恢复并不是毫无限制：它有 Thread/Goal 绑定、重启次数限制，也明确禁止复播旧写入，这些原则值得保留。问题是这些流程分散在 launcher、Bridge、Panel、runtime 之间。

我会把默认恢复降为：

**保留检查点 → 呈现崩溃事实 → 用户选择恢复 → 新 runtime 建立身份 → 查询/观察实际场景 → Codex 继续。**

无人值守 Goal 的自动恢复可以后续重新接入，但应基于新的 operation 协议，不再靠多个模块互相猜测。

---

## 各部分最终处置建议

| 处置           | 具体内容                                                              |
| ------------ | ----------------------------------------------------------------- |
| **保留**       | Codex App Server、批量 HOM、动态安装能力查询、主线程执行、原生图片回传、定向差异、显式记忆、版本化契约     |
| **直接移除默认依赖** | 启动时知识构建、lexical 启动对完整 embedding contract 的依赖、普通场景任务对插件开发资料的默认依赖   |
| **允许删除**     | FX fallback/B2 专用通道及其启动强制契约、重复 capability discovery、随被删除机制失去意义的测试 |
| **简化**       | 全局长提示、默认执行证据、重复验证轮次、scope 与目录约定、Panel 的流程控制状态                     |
| **重写**       | Scene identity、operation lifecycle、结果收据与重连查询、workspace 身份边界       |
| **外置为可选能力**  | 复杂资料导入、embedding 安装与构建、语义检索增强、专门的效果实验                             |
| **后续处理**     | IPC 微优化、ANN 实现、更多缓存、界面美化、更多平台兼容                                   |

注意，**版本化 contract 本身不应删除**。一组经过测试的 Codex 版本与对应协议契约能防止接口漂移。应该删除的是已经不参与目标产品的旧协议负担，而不是所有 schema 和版本约束。

---

## 怎样避免变成无限期重写

这次重写应以三个可验收结果封口：

**第一，场景执行有权威状态。** 不再把 Turn 状态当成 HOM 状态，不再丢失响应就丢失操作事实。

**第二，普通任务有低成本闭环。** 已知参数修改无需 knowledge、全场景检查或截图；复杂任务按有意义的阶段推进。

**第三，可选基础设施不能拖住核心产品。** 没有向量模型、没有导入库、没有自动恢复系统，Panel 仍能稳定驱动 Codex 操作当前 Houdini。

达到这三个结果后，就应该回到真实 Houdini 创作任务迭代，而不是继续追求一套“完美的 Agent 平台”。

---

# 最后的结论

**这不是一个核心方向错误的项目，而是一个把不少外围问题处理得很细，却尚未把最关键的执行事实收敛到单一权威来源的项目。**

你对复杂度的担忧有根据，但不是所有复杂度都该删：

主线程调度、身份校验、定向验证、图片证据、明确的失败处理，值得投入；多套运行状态、安装目录与用户项目混用、同步知识构建、过度宽泛的执行报告，不值得继续沿原方向累积。

**最先应该重写的是场景操作协议和状态归属。最先应该移出关键路径的是知识初始化与构建。最先应该优化的 Agent 成本，是重复观察、重复验证和过重结果，而不是单纯把工具数量从 18 改成 7。**

下一版的目标应该很具体：

> **Codex 提交一个有明确目标的 HOM 批次；系统确保它作用于正确的场景，可靠记录执行结果，只返回下一步决策所需的证据；发生中断时，所有部分都知道哪些事实确定、哪些仍然未知。**

围绕这个目标重构，复杂度才会真正下降，插件完成 Houdini 工作的速度和稳定性才会一起提高。
