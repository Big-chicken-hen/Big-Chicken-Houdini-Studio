## 审查结论

**目前不能把这次 10048 定性为“Studio 导致系统端口耗尽”，也不能据此归咎于 Clash。但是，在 RC 对应源码中，已经能确认一个独立的发送恢复缺陷：请求尚未开始发送，就可能被错误归入“发送结果未知”，随后进入无法通过现有查询流程解除的状态。**

因此，我建议：**新开连接问题单，保持功能冻结，只对取证、发送失败分类及必要的恢复控制小范围解冻；不要现在就重写网络层，也不要要求用户关闭 Clash。**

## 一、现有证据支持什么，不支持什么？

### 1. 系统确实值得沿“端口压力”方向调查，但因果链还没有闭合

按你提供的摘要，Tcpip 4231、4227 是重要证据，不应该被当作普通噪声忽略。不过，微软的排查文档也明确区分了“有很多 TIME_WAIT”和“已经发生端口耗尽”：**大量 TIME_WAIT 本身不足以单独证明耗尽，更不能直接确定责任程序。**([Microsoft Learn][1])

目前可以这样分级：

| 判断                                 | 当前评价                        |
| ---------------------------------- | --------------------------- |
| Windows 曾出现临时端口分配／连接建立方面的问题        | **有较强线索**，需要原始事件和时间戳核对      |
| 截图中的 10048 就由上述端口问题直接引起            | **尚未证实**，缺少失败调用位置和时间关联      |
| Studio 是约 2.15 万条 TIME_WAIT 的主要制造者 | **尚未证实**                    |
| Studio 的短连接会贡献连接创建与关闭负载            | **源码可以确认**                  |
| 因为连接有 `close()`，Studio 就不可能有责任     | **不成立**；资源关闭与连接创建频率是两个问题    |
| 多数 TIME_WAIT 非纯回环，所以一定与 Studio 无关  | **不成立**；还必须考虑其子进程、外部连接及代理链路 |

另外，10048 表示地址已被使用，**不能只凭错误编号就认定“某个本地服务的监听端口被占了”**。Winsock 文档指出，客户端连接也涉及本地地址／端口分配，相关错误可能在 `connect()` 等调用处出现。([Microsoft Learn][2])

### 2. “点击发送时看到了错误”，不等于失败的就是发送请求

这是本次源码审查中很值得注意的一点。

Panel 的状态轮询、事件读取、历史读取、发送及提交查询，都可能向同一个通知区域显示错误。例如，`refresh()` 发出的 `/events` 请求没有独立的错误展示通道，其失败也会进入 Panel 的通知逻辑。因此：

**截图中的 10048 可能来自 `/turn` 或 `/turn/steer`，也可能来自同时发生的 `/state`、`/events` 或后续 `/reconcile`。**

在拿到“具体路由＋失败阶段”之前，不能根据用户点击动作判断是哪一次 HTTP 请求失败。

### 3. 关于 Clash，目前既不能归责，也不能完全排除环境交互

源码中有两条明确的本地通信边界：

* Panel 的 `_HttpJob` 使用 socket 直连经过校验的 `127.0.0.1`，没有应用层代理、重定向或自动重试路径。
* Bridge 使用的 `http.Client` 明确配置 `ProxyHandler({})`，本地调用不依赖系统 HTTP 代理配置。

这支持的是：**不能把 Panel 本地 HTTP 故障直接解释成“它错误地走了 Clash 的 HTTP 代理”。**

但它并不证明整台机器不存在共享端口压力，也不能说明所有非回环连接都来自无关软件。后续应在 **Clash 正常运行** 的条件下识别连接来源，而不是通过关闭必需环境来换取一次表面正常。

## 二、源码里有哪些实际问题？

### A. 高优先级：连接建立前失败，也被标成“发送结果未知”

**这是本次最明确、最值得优先处理的代码问题。**

相关位置：

`src/studio/ui/shared.py` → `_HttpJob.exchange()`

其执行顺序是先创建 socket，再调用：

```python
active.connect((endpoint.hostname, endpoint.port))
```

之后才进入：

```python
connection.request(...)
```

但目前所有捕获到的 `OSError`、`HTTPException`，都被统一转换为：

```python
ApiFailure(
    ...,
    code="CONNECTION_LOST",
    submission_state="unknown",
)
```

**所以，即使 `connect()` 就失败、这次 HTTP 请求根本没有开始写出，也会被当成“可能已经送达”。**

这不是单纯提示文字不准确，它会与后续业务状态机形成问题链：

| 阶段                   | 当前行为及后果                             |
| -------------------- | ----------------------------------- |
| 用户点击发送／补充            | Panel 创建消息 ID、保存本地快照，并清空当前输入区       |
| socket 建立连接失败        | 被归类为 `unknown`                      |
| `send_failed()`      | 保持原提交待确认，并尝试查询原消息身份                 |
| Bridge 从未收到该 POST    | 自然不存在这条消息记录                         |
| `Bridge.reconcile()` | 返回 `INPUT_RECORD_UNAVAILABLE`       |
| `reconcile_failed()` | 显示错误，但不解除 `uncertain_send`          |
| 网络恢复                 | 正常状态轮询本身不能为不存在的记录产生确认结果；发送入口可能继续被阻止 |

这条条件路径可以从发送、查询与失败处理代码直接推导出来。**尚未证明用户这次事故确实走了它，但这个恢复缺口本身值得独立开单，不必等查明两万多条连接的来源才承认。**

**修复时有两个关键边界：**

第一，只能依据**同一条发送请求**的明确阶段证明“尚未发送”。不能因为某个后台 `/state` 请求连接失败，就推断同时进行的消息 POST 也没发出去。

第二，不能用 `HTTP status is None` 判断“未发送”。请求可能已经写出，只是尚未收到响应头。应记录“是否已经进入请求写出阶段”，并在进入可能写出数据的操作**之前**改变阶段标记。

还有一个需要一起验证的竞态：Panel 的连接代次变化会屏蔽旧回调；若后台状态请求先失败，随后原发送请求才回报“确定未发送”，这一终态也可能被代次屏蔽。**修复不能简单放开全部旧回调，而应按原消息身份安全地处理原提交的终态。**

### B. 确认存在持续短连接负载，但没有发现“明显漏关 socket”的证据

当前 `_HttpJob.exchange()` 的 `finally` 会关闭响应、HTTPConnection 和原始 socket；取消请求时也会执行 shutdown／close，并禁止 `HTTPConnection` 自动重新建立连接。Panel 的 `closeEvent()` 会停止四个相关定时器，并关闭它拥有的 Api。**这些不是没有清理的实现。**

因此，目前不应把问题写成：

> “已经确认 socket 泄漏，忘记 close 导致端口耗尽。”

更准确的是：

> **当前采用逐请求短连接设计；即使用户态资源正常关闭，也需要评估其连接周转量以及故障期间的行为。**

### C. 轮询有防重叠保护，但断连后的退避不足

源码中：

* 每 **850 毫秒**刷新 `/state` 和 `/events`。
* 每 **8 秒**刷新 `/account`。
* 这些基础轮询使用 `unique=True`，同一 Api 内对应路由已有请求未完成时，不再新增相同路由请求。
* `connection_failed()` 不停止基础轮询，也没有调整轮询间隔。

所以，这里应区分：

**没有证据表明基础轮询每 850 毫秒无界堆积一批请求；但是，在连接快速失败时，它会持续按固定频率重新尝试。**

还有一层容易漏算：Bridge 每处理一次 `/state`，又会向 Runtime 发起一次 `/health` 请求。

按源码间隔计算，在请求都能及时完成、没有额外操作的假设下：

| 范围                                  |                推算的基础请求频率 |
| ----------------------------------- | -----------------------: |
| 单个 Panel → Bridge                   |           约 **2.48 次／秒** |
| 加上该 Panel 触发的 Bridge → Runtime 健康检查 | 约 **3.65 次本地 HTTP 交换／秒** |

这是**设计频率推算，不是现场测量，也不等于每秒新增同样数量的 TIME_WAIT**。它说明 Studio 的连接负载不是零；但仍不能用它直接解释 2.15 万条快照。

建议将“失败退避、恢复时合并刷新、多 Panel 时的总负载”列入本轮评估，而不是直接认定正常轮询频率就是事故主因。

### D. 历史刷新不是无限自动重试，但连接抖动值得补测

历史读取已有 `hydrating` 防重叠、请求身份校验、连接代次隔离，以及一次有界自动补读；补读失败后会停止本轮自动恢复。**不能笼统描述成“历史失败后不停重试”。**

不过，连接变化会重置历史恢复状态，恢复连接后又会触发历史加载。因此，反复断连／恢复、手动重连与慢历史请求交错时，仍需要检查旧工作请求是否及时退出、是否产生不必要的新请求。

我把这一项归为**需要定向测试的次级风险**，不是已经确认的泄漏。

### E. 诊断信息不足是确定的问题

当前本地传输异常主要保存 `str(error)`、通用错误码和提交分类，没有保留明确的：

`失败阶段、异常类型、winerror/errno、请求路由、关联消息身份、异常调用栈`。

外层还有将异常转换成通用连接错误的兜底。这能解释为什么最终只留下一个 Windows 错误字符串，却不能确认它来自哪次请求、哪个调用。

这是适合小范围补强的地方，不需要动认证、配置或场景逻辑。

## 三、下一步最有价值、干扰最小的验证是什么？

我建议做**两条并行但互不依赖的验证线**：一条定位现场端口问题，一条验证已发现的恢复缺陷。

### 第一条：围绕一次真实错误取得关联证据

不要先重启机器、关 Clash、清配置或修改 TCP 参数。先取得**同一个故障时间窗口**内的以下信息：

| 材料        | 最关键内容                                                |
| --------- | ---------------------------------------------------- |
| 实际运行身份    | Panel／Bridge 加载位置、版本身份、当前工作树提交与相关未提交差异               |
| 一次错误的请求记录 | 时间、路由、请求 ID、失败阶段、异常类型、`winerror`、调用栈；若是发送，再关联原消息 ID  |
| 系统网络证据    | 4231／4227 原始事件；同窗口 IPv4／IPv6 连接快照、状态和端点分布            |
| 进程对应关系    | Houdini、Bridge、Codex、Clash 等相关进程的 PID、启动时间、父子关系及连接变化 |

这里最重要的不是再取得一张“总共多少 TIME_WAIT”的截图，而是回答：

> **报错发生时，是哪个进程、向哪个端点、在什么阶段失败？在它失败之前，哪些进程的连接创建或占用正在增长？**

采样应同时关注活动连接与 BOUND 等状态，不能只看事后 TIME_WAIT 总数。微软的排查路径也强调按进程识别端口占用，并在必要时使用网络事件跟踪进一步确认。([Microsoft Learn][1])

如果现有日志不足，可批准一个**默认关闭、仅本地保存、有容量限制的诊断开关**：异常时保存脱敏堆栈，平时按时间窗口累计路由请求数、成功／失败数、在途数。不要记录请求正文、认证头、完整环境变量或聊天历史。

### 第二条：在隔离测试中注入“连接前失败”

这条验证更直接，而且**不需要把用户机器真的耗尽端口**。

在测试中的 `_CancellableSocket.connect()` 注入一个带 10048 信息的 `OSError`，分别走发送与补充流程，检查：

**HTTP 请求是否完全没有写出；Bridge／Codex 是否零接收；Panel 是否错误进入 unknown；连接恢复后是否仍无法继续发送；原文和图片是否仍可取回。**

然后加上“后台 `/state` 同时失败、先推进连接代次”的竞态变体。

已有生命周期测试覆盖了响应丢失、截断响应、不重放、关闭取消和 Stop 不被普通线程池阻塞，但我检查的这组测试没有覆盖“`connect()` 失败后，完整消息恢复状态机如何收口”这一组合。

**这应当是下一步优先级最高的代码侧验证。**

### 需要特别保护：当前原文保留，不等于一定已经落盘

Panel 在发送前保留的是自身内存里的提交快照；Bridge 的未确认输入持久化发生在收到请求并执行 `reserve()` 之后。**若连接建立前失败，Bridge 根本没机会保存这条消息。**

所以现在不建议把“关掉 Panel 再开”“重启 Houdini”当第一步恢复手段。应先保存未确认原文、正在编辑的新草稿及附件引用，再决定后续动作。**目前没有证据表明场景或既有历史已被破坏，但也不能把内存保留误称为跨重启保全。**

## 四、需要修复时，建议多大范围？

### 建议优先批准的最小范围

| 修复项             | 建议涉及范围                     | 主要约束                      |
| --------------- | -------------------------- | ------------------------- |
| 传输失败阶段与脱敏诊断     | `ui/shared.py`，必要的服务端诊断位置  | 不记录正文、token、完整环境          |
| 确定未发送与结果未知的正确分类 | `_HttpJob` 与 Panel 原提交终态处理 | 仅凭同一请求的明确证据分类；不能放松不确定提交保护 |
| 故障期间有界退避、恢复刷新合并 | Panel 轮询／重连调度              | 保留在途去重；不把发送请求放入自动重发队列     |
| 新的故障和竞态回归       | 传输、Panel、提交恢复测试            | 不修改真实用户场景与历史              |

**暂不建议纳入本轮：**更换整个网络框架、重写消息存储、迁移认证、改 Houdini 环境变量、调整全局代理、固定监听端口、修改系统 TCP 回收参数。

### 不要把“删掉 `Connection: close`”当作完整修复

当前服务端 `Handler` 没有设置 HTTP/1.1 协议版本；标准库默认是 HTTP/1.0。启用持久连接需要客户端复用与服务端协议、响应边界等共同配合，不是改一个请求头就结束。([Python documentation][3])

而且现有服务端有 **32 个并发处理槽位**。若引入长连接，还要评估空闲连接占用、连接池上限、损坏连接淘汰、取消行为，以及长历史请求是否妨碍 Stop。

因此，**连接池属于需要单独设计和验收的中等范围修改，不是当前 RC 应凭猜测立即接受的小补丁。**应先用现场数据确认它是不是必要。

同样，不建议为绕过这次故障退回旧的 QNetworkReply 传输实现。原 NET-1 记录有明确的对象身份错配证据，替换它有具体原因；新问题不能成为撤销旧修复的充分依据。

### 必要回归检查

| 场景                    | 必须满足的结果                              |
| --------------------- | ------------------------------------ |
| 发送／补充在连接前失败           | 明确未发送，原文保留，恢复后可由用户重新提交；不自动发送         |
| 请求可能部分写出，或服务端已接纳但响应丢失 | 继续保持 unknown，查询原 ID，不重复提交            |
| 后台轮询失败与发送终态交错         | 不遗失原提交的确定结果，也不跨账号／会话错误应用旧结果          |
| 慢历史、双 Panel、断连恢复、关闭重开 | 在途数与工作请求数能回落，旧回调不污染新状态               |
| 普通请求工作池被占满时 Stop      | 保留独立处理能力；网络不通时明确“停止未确认”，不能假称已停止      |
| 当前任务结束、切换或已请求停止时补充    | 不错投其他 Turn，不把失败补充自动变成下一轮新任务          |
| Clash 保持正常使用的实际环境     | 本地通信边界不变，外部登录与模型通信不受破坏               |
| 实际 RC 包的长时运行          | 覆盖此前出现问题的使用时长，记录连接趋势与恢复情况，而不只是短时间零报错 |

对于恢复正确性，验收重点应是**不重复、不丢失、不永久卡住**；对于端口问题，验收重点应是**来源可解释、负载有界、故障后能恢复**，而不是要求 TIME_WAIT 永远为零。

## 最需要补充的材料

不必先上传整个项目或全部聊天历史。最关键的是：

**第一，实际运行版本与源码差异。**确认当前加载的 `ui/shared.py`、`ui/panel.py`、`http.py`、`bridge.py` 是否与 `e6beb5a` 一致；有差异就提供这些文件的差异及实际加载路径。

**第二，一次错误的完整关联记录。**包括准确时间、Panel 错误详情、具体请求路由、异常堆栈；若关联发送，再附原消息 ID 的脱敏状态记录，不需要消息正文。

**第三，同一时间窗口的系统事件与连接／进程数据。**尤其是两份现有连接快照的原始输出、采集时间、IPv4／IPv6 范围，以及相关进程对应关系。

**最终建议：先验证“连接前失败导致恢复卡住”这条确定的代码路径，同时采集现场端口来源；随后只修有证据支持的部分。保留 Clash、现有场景、认证与历史，不用大范围重构来替代定位。**
